# COMPLIANCE OS — DEPLOY RUNBOOK

Decision D17 (2026-09-17). Topology: **web on Vercel** (São Paulo functions, `gru1`), **API + daily
job + PostgreSQL on Render** (blueprint `render.yaml`, region Ohio — the closest Render region to
Brazil), **files on any S3-compatible bucket**, **e-mail through any SMTP relay**. The browser only
ever talks to the web domain: the Next.js BFF (`/api/v1/*`) proxies to the API, so cookies stay
first-party and the API needs no public CORS beyond the web origin.

```
browser ── https://app.<domain> (Vercel, gru1) ──BFF──> https://<api>.onrender.com (Render, ohio)
                                                             │            │
                                                     PostgreSQL 16   S3 bucket · SMTP relay
                                              cron 08:00 BRT: scripts/send_reminders.py
```

## 0. What CI already proves on every push (`.github/workflows/ci.yml`)

production Docker image builds, boots against PostgreSQL (migrations + content seed + `/health`),
runs the reminders job, and **refuses to start** with an incomplete production configuration.

## 2. API + database + job on Render

1. Render → **New → Blueprint** → pick the repository → Render reads `render.yaml` and shows the
   values marked `sync: false`. Fill them:

   | Variable | Value |
   |---|---|
   | `CORS_ORIGINS` | JSON list with the web origin: `["https://app.<domain>"]` (add the `*.vercel.app` preview origin only while testing) |
   | `APP_BASE_URL` | `https://app.<domain>` (used in e-mail links) |
   | `SMTP_HOST`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM` | relay credentials; `SMTP_FROM` like `Compliance OS <no-reply@<domain>>` |
   | `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | bucket credentials; `S3_ENDPOINT_URL` only for non-AWS providers |

   `JWT_SECRET` is generated by Render; `DATABASE_URL` comes from the blueprint database (the
   `postgres://` form is normalized by the API). `APP_ENV=production` turns on the guards: the
   service will not start without HTTPS cookies, SMTP, S3 and a 32+ character secret.
2. Apply. The first deploy runs `alembic upgrade head` and `scripts/seed_content.py` (assessment
   template v1) in the container entrypoint, then serves. Health check: `GET /health`.
3. Copy the service URL (`https://compliance-os-api-XXXX.onrender.com`) — the web app needs it.
4. Optional demo organization (never on a customer instance): Render → service → Shell →
   `python scripts/seed_demo.py --password '<strong password>'`.

Scaling note (D23): the rate limiter is in-memory per process — `WEB_CONCURRENCY=1` and a single
instance keep the limits exact. Before running more than one instance, back the limiter with the
managed Redis (Key Value) and record it in D23.

## 3. Web on Vercel

1. Vercel → **Add New → Project** → import the repository → **Root Directory: `apps/web`**
   (`apps/web/vercel.json` pins the framework and the `gru1` region).
2. Environment variables (Production and Preview): `API_BASE_URL=https://<render service url>`.
   Nothing else — the web app holds no secrets.
3. Deploy. Then set the custom domain (`app.<domain>`) and update `CORS_ORIGINS` / `APP_BASE_URL`
   on Render to that final origin.

CLI equivalent from `apps/web`: `vercel link` → `vercel env add API_BASE_URL production` →
`vercel --prod`.

## 4. First login and smoke test

1. `https://app.<domain>/criar-conta` → create the first account and organization; the welcome
   flow leads to the diagnostic.
2. Confirm: password-reset e-mail arrives (SMTP), a file uploads and downloads (S3), `/historico`
   shows the actions, `https://<api>/health` returns the version.
3. Check the Render cron job ran once (Logs) the next morning.

## 5. Operations

- **Migrations** run on every deploy before the new version serves. Every migration ships with a
  tested `downgrade`; to roll back code *and* schema: Render → Rollback to the previous deploy, then
  Shell → `alembic downgrade <previous revision>`.
- **Backups**: Render PostgreSQL daily backups on paid plans; take a manual backup before a release
  that adds a migration. Files live in the bucket (versioning recommended).
- **Logs**: JSON-ish single lines with `request_id`; the web app forwards `X-Request-ID` so a user's
  report maps to one API log line. Never log bodies (D19).
- **Secrets rotation**: `JWT_SECRET` rotation logs every user out (access tokens 15 min, refresh
  cookies become invalid). SMTP/S3 keys rotate in the dashboard; redeploy picks them up.
- **Compliance Room** (D36): public links are served by the same API; the limiter caveat above
  applies to its per-IP limits.
- **Agent LLM** (D35): off (`LLM_PROVIDER=none`) until D13 and the D35 legal review are recorded;
  then add `LLM_PROVIDER=anthropic` and `ANTHROPIC_API_KEY` on the service and redeploy.

## 6. Data residency (read before onboarding customers)

Render has no Brazilian region: the database lives in Ohio (US). LGPD treats this as an
international transfer of the customers' personal data (member names, e-mails, and whatever they
type into risks and documents) — legal basis and contractual safeguards are part of D12/D13
(sources-v1.md B4) and require human legal review. If the review requires data at rest in Brazil,
the proven alternative is **Fly.io (region `gru`) for the API + Neon (`sa-east-1`) for PostgreSQL**:
the image, entrypoint and environment are identical; only the blueprint changes. Keep API and
database in the same region either way — the app issues several queries per page.

## 7. Not automated on purpose

Account creation, secrets and payment details are typed by a person in each provider's dashboard;
nothing in this repository can create accounts or hold credentials.
